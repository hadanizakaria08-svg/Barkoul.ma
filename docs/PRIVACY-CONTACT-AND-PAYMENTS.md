# Barkoul.ma — متطلبات خصوصية الاتصال والمدفوعات

> هذه وثيقة متطلبات قبول ملزمة للتطوير والاختبار. ليست دليلاً على تنفيذ هذه الضوابط أو على حماية قاعدة الإنتاج.

## 1. تصنيف البيانات

| التصنيف | أمثلة | القاعدة |
|---|---|---|
| عامة | المدن، نوع الحمولة، نوع الشاحنة، تاريخ تقريبي | لا تتضمن هوية أو وسيلة اتصال |
| داخل المنصة | عروض الأسعار، حالات الشحنة، بيانات الرحلة | لا يراها إلا صاحب الشحنة والسائق المرتبط والإدارة المخولة عند الحاجة |
| شخصية | الاسم، الهاتف، البريد، بيانات الحساب | لا تظهر في نتائج التصفح العامة |
| شديدة الحساسية | وثائق الهوية/السياقة، بيانات المركبة الخاصة، موقع مباشر | تخزين خاص ووصول محدد ومؤقت وسجل وصول |
| مالية | استحقاق العمولة، إثبات الدفع، مرجع مزود الدفع | سجل مالي موثوق غير قابل للتعديل من العميل |

## 2. الاتصال والرسائل الخاصة

- لا تُعرض أرقام الهاتف أو البريد أو أي معرّف شخصي في بطاقة الشحنة العامة أو استعلام التصفح العام.
- لا يفتح اتصال خاص إلا بين الأطراف المرتبطة فعلياً بعرض/اتفاق/رحلة صالحة وفق سياسة كشف اتصال يعتمدها مالك المنتج.
- كل محادثة مرتبطة بسياق شحنة واتفاق، ولا يسمح للمستخدم باختيار معرف محادثة لطرف آخر أو قراءة رسائله.
- فرض صلاحية القراءة والإرسال على مستوى قاعدة البيانات لكل رسالة: هوية الجلسة الموثقة يجب أن تكون أحد المشاركين الفعليين.
- منع تعديل المرسل أو المستلم أو الشحنة أو الرحلة من العميل؛ تُشتق هوية المرسل من auth.uid() داخل مسار موثوق.
- لا تُرسل رسائل أو بيانات اتصال إلى سجلات التحليلات أو سجلات الأخطاء.
- لا تمنح الإدارة وصولاً شاملاً افتراضياً إلى محتوى المحادثات. معالجة البلاغات يجب أن تكون محدودة ومبررة ومسجلة.
- تشفير النقل عبر HTTPS/WSS، والاستفادة من تشفير التخزين لدى مزود قاعدة البيانات، مع عدم الادعاء بتشفير طرف إلى طرف ما لم ينفذ ويختبر فعلياً.
- منع الروابط والملفات الضارة، وتحديد أطوال الرسائل ومعدل الإرسال ومكافحة الرسائل المزعجة.
- عند الحظر أو إلغاء الاتفاق، تُوقف صلاحيات الاتصال وفق سياسة واضحة، مع الاحتفاظ بالقدر اللازم للنزاعات والالتزامات القانونية.

## 3. أرقام الهواتف وكشف بيانات الاتصال

- القيمة الافتراضية: مخفية.
- لا يُكشف الرقم لمجرد تصفح الشحنة أو تسجيل الحساب أو تقديم عرض غير مقبول.
- أي استثناء للكشف يجب أن يرتبط بحالة عمل مؤكدة، ويكون محدوداً بالطرفين وبمدة الرحلة، ويسجل الحدث دون نسخ الرقم إلى السجلات.
- يجب اختبار محاولات قراءة الرقم مباشرة من REST/API أو عبر تغيير معرف الشحنة/الرحلة.
- لا يكفي إخفاء الرقم في React أو تعطيل زر الاتصال.

## 4. وثائق السائقين والتخزين

- حاوية الوثائق private فقط، ولا تستخدم روابط عامة دائمة.
- مسار الملف يتضمن معرف المالك الموثوق ولا يقبل client-supplied owner ID.
- سياسات Storage تمنع الرفع والقراءة والتعديل والحذف لغير المالك أو المراجع المخول.
- الروابط الموقعة قصيرة العمر، تصدر بعد التحقق من الدور والغرض.
- حدود للحجم والامتداد وMIME، وفحص محتوى الملفات قبل اعتمادها متى توفرت بيئة فحص.
- لا تُحفظ صور الوثائق داخل cache أو service worker أو سجلات المتصفح.
- لا تُقبل وثيقة تحقق عبر رابط عام أو من مستخدم غير مصادق.

## 5. العمولات والسجل المالي

القيم التجارية الحالية:
- 10 MAD على صاحب الشحنة.
- 20 MAD على السائق.
- الاستحقاق عند تحقق تعريف «نقل ناجح» المعتمد، وليس عند مجرد إنشاء الشحنة أو تقديم عرض.

قواعد تقنية:
- حفظ المبالغ كأعداد صحيحة بوحدة السنتيم لتجنب أخطاء الفاصلة العشرية.
- إنشاء سجلين منفصلين للاستحقاق (صاحب الشحنة والسائق) مرتبطين بمعرف رحلة واحد.
- قيد فريد يمنع إنشاء استحقاق مكرر لكل طرف ولكل رحلة.
- لا يحدد المتصفح أن الرحلة ناجحة ولا يحسب المبلغ النهائي؛ الانتقال المالي يتم داخل معاملة موثوقة.
- سجل مالي append-only قدر الإمكان: لا حذف أو تعديل مباشر للأحداث السابقة؛ التصحيح عبر قيد عكسي موثق.
- حفظ المبلغ والعملة والطرف والحالة والسبب والطابع الزمني ومعرف العملية، دون تخزين بيانات بطاقة الدفع.

## 6. الدفع النقدي والإلكتروني

### النقدي
- تسجيل أن العمولة مستحقة ثم تسجيل التحصيل كحدث منفصل.
- تحديد من أكد الدفع، ومتى، ولمن، وربطه بالرحلة والعمولة.
- منع التأكيد المكرر، وإتاحة الاعتراض/النزاع بدلاً من تعديل السجل القديم.
- لا تعتبر المنصة المبلغ مدفوعاً لمجرد ضغط المستخدم على زر «دفعت».

### الإلكتروني
- لا تخزن Barkoul.ma أرقام البطاقات أو CVV أو كلمات مرور المحافظ.
- مزود الدفع يعالج بيانات الدفع، والمنصة تحفظ مرجع المعاملة والحالة والمبلغ والعملة فقط.
- تأكيد الدفع من webhook موثوق مع التحقق من التوقيع والمبلغ والعملة والمرجع، وليس من redirect أو نتيجة يرسلها المتصفح.
- idempotency ومفاتيح فريدة لمنع تكرار الدفع أو webhook.
- معالجة الفشل والإلغاء والاسترجاع والنزاع مع سجل حالة واضح.
- لا اختيار لمزود أو تشغيل دفع حقيقي قبل مراجعة الرسوم والشروط والتوافق في المغرب وموافقة مالك المشروع.

## 7. حماية الحسابات والأجهزة

- استخدام PKCE لتدفقات المصادقة.
- عدم تخزين service_role أو مفاتيح سرية في تطبيق الويب أو تطبيقات الهاتف.
- انتهاء الجلسات وتسجيل الخروج وإبطال الجلسة عند الحاجة، واختبار تبديل الحسابات على الجهاز نفسه.
- تحديد معدلات محاولات الدخول والاستعادة وإرسال الرسائل على مستوى إعدادات المزود/الخادم.
- رسائل أخطاء عامة لا تكشف وجود حساب أو تفاصيل داخلية.
- لا تخزن بيانات خاصة في localStorage أو IndexedDB أو Service Worker إلا بعد تقييم أمني ومبرر واضح؛ لا تخزن المحادثات والوثائق وبيانات الدفع في cache التطبيق.

## 8. الموقع والإشعارات

- لا مشاركة لموقع السائق بشكل دائم.
- الموقع الدقيق، إن أضيف، يشارك فقط بموافقة المستخدم ولغرض رحلة نشطة ولمدة محدودة.
- لا تضع أرقام الهاتف أو محتوى الرسائل أو بيانات الدفع في إشعارات شاشة القفل.
- إشعارات WhatsApp/SMS/Push أو مزود خارجي لا تضاف قبل مراجعة التكلفة والخصوصية والموافقة.

## 9. اختبارات القبول الإلزامية

1. الزائر لا يحصل على هاتف أو بريد أو وثيقة أو رسالة خاصة.
2. صاحب شحنة لا يقرأ محادثة أو وثائق سائق غير مرتبط به.
3. سائق لا يقرأ بيانات أو محادثة تخص شحنة لم يُقبل فيها طرفاً.
4. تغيير UUID/ID في الطلب لا يكشف بيانات شخص آخر (اختبار IDOR).
5. إرسال sender_id أو owner_id مزور يرفضه الخادم.
6. مستخدم عادي لا يقرأ أو يغير دور admin.
7. مستخدم غير مشارك لا يستطيع قراءة الرسائل حتى بطلب API مباشر.
8. ملف وثيقة غير مصرح به أو من نوع/حجم ممنوع يُرفض.
9. تكرار طلب إتمام الرحلة أو webhook لا يكرر العمولة أو الدفع.
10. لا يمكن اعتماد الدفع الإلكتروني من صفحة العودة وحدها.
11. لا يمكن لطرف واحد تزوير تأكيد نقدي نيابة عن الطرف الآخر.
12. لا تحتوي سجلات التطبيق على كلمات مرور أو access/refresh tokens أو محتوى الرسائل أو وثائق.
13. لا يخزن Service Worker استجابات Supabase أو روابط استعادة الحساب أو رموزها.
14. اختبار النسخ الاحتياطي والاستعادة والتراجع قبل الإطلاق.

## 10. بوابات التنفيذ

- مطابقة المخطط الحي والسياسات الحالية أولاً.
- تصميم واختبار migrations في مشروع Supabase منفصل.
- اختبار كل دور عبر API مباشر واختبارات سلبية.
- تنفيذ الاتصال والوثائق والعمولات كعمليات خادمية/معاملات موثوقة.
- اختبار مزود الدفع في وضع sandbox فقط بعد اختيار وموافقة.
- لا تنشر أو تطبق migration على الإنتاج دون موافقة صريحة.
