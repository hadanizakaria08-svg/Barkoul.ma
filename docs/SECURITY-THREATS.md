# Barkoul.ma — نموذج التهديدات وخطة الضوابط الأمنية

## النطاق والأصول
الأصول المطلوب حمايتها: حسابات المستخدمين والجلسات، أرقام الهواتف والبيانات الشخصية، الشحنات وملكيتها، عروض التفاوض، الرحلات، وثائق السائقين، بيانات الإدارة، وسجلات العمولات والتحصيل.

## نموذج الخصم
نفترض أن أي متصفح أو تطبيق عميل قد يكون معدلاً بالكامل، وأن المستخدم قد يرسل طلبات مباشرة إلى Supabase دون المرور بالواجهة. لذلك لا تعد شروط React أو TypeScript أو إخفاء الأزرار حدوداً أمنية. المفتاح العام الخاص بـSupabase ليس سراً؛ الحماية يجب أن تأتي من RLS والقيود والعمليات الموثوقة.

## التهديدات والضوابط المطلوبة

| التهديد | الضابط الأساسي | اختبار القبول |
|---|---|---|
| قراءة بيانات مستخدم آخر | RLS على كل جدول مكشوف، مع سياسة deny-by-default حيث أمكن | مستخدم A لا يقرأ بيانات B الخاصة |
| تزوير owner_id أو driver_id | اشتقاق الهوية من auth.uid() داخل PostgreSQL/عملية موثوقة | طلب مباشر بهوية مزورة يُرفض |
| رفع الدور إلى owner/admin | منع تحديث role ذاتياً، مسار إدارة موثوق ومراجع | مستخدم عادي لا يرفع دوره حتى بطلب REST مباشر |
| التفاوض على شحنة ذاتية أو مغلقة | فحص المالك والحالة في عملية موثوقة مع قيد مناسب | الطلب المباشر يفشل في الحالتين |
| قبول عرضين متزامنين | معاملة ذرية/قفل أو تحديث مشروط بالحالة الحالية | لا يمكن أن ينتج اتفاقان متعارضان |
| تكرار الرحلة أو العمولة | مفتاح idempotency وقيد فريد ومعاملة واحدة | إعادة نفس الطلب لا تنشئ أثراً مكرراً |
| كشف بيانات الاتصال | سياسة كشف بعد تحقق شروط العملية | الزائر والسائق غير المتفق لا يحصلان على الرقم |
| XSS وحقن المدخلات | ترميز سياقي، تحقق خادمي، وعدم إدراج HTML غير موثوق | نصوص هجومية تظهر كنص ولا تنفذ |
| سرقة الجلسة أو إساءة استخدام جهاز مشترك | إعدادات Auth الآمنة، انتهاء الجلسة، تسجيل خروج واختبارات دورة الحياة | الخروج يلغي الوصول الخاص من الجلسة |
| رفع ملف خبيث أو منتحل | Storage policies، حد الحجم، MIME/امتداد، فحص محتوى عند توفره | لا يقبل ملف غير مصرح أو يتجاوز الحد |
| تخمين كلمات المرور/إساءة API | حدود Auth ومعدل الطلبات ومراقبة الأنماط | تقييد المحاولات دون كشف وجود الحساب |
| تسريب الأسرار | منع service_role والرموز وكلمات المرور من الواجهة والسجلات | فحص المستودع والبناء لا يجد أسراراً |
| العبث بسجلات الإدارة | كتابة سجل التدقيق من مسار موثوق ومنع التعديل/الحذف العام | لا يستطيع مستخدم عادي تغيير سجل التدقيق |

## طبقات الحماية المستهدفة

1. **الواجهة:** تحقق تجربة الاستخدام فقط؛ لا تُعامل كمرجع للصلاحيات. React يجب أن يعرض مدخلات المستخدم كنص عادي، وألا يستخدم HTML غير موثوق.
2. **طبقة البيانات:** allow-list لحقول الإدخال، واستخراج هوية المستخدم من جلسة موثقة، ومعالجة الأخطاء دون تسريب رموز أو بيانات حساسة.
3. **PostgreSQL / Supabase:** RLS، grants محدودة، قيود ومفاتيح أجنبية، دوال موثوقة بصلاحيات مضبوطة وsearch_path آمن، ومنع تصعيد الأدوار.
4. **العمليات الحساسة:** التفاوض والقبول والرحلات والعمولات يجب أن تكون ذرية وتتحقق من الحالة والملكية داخل قاعدة البيانات أو وظيفة موثوقة، لا في المتصفح فقط.
5. **التخزين:** لا تفعيل لرفع الوثائق قبل تدقيق buckets وسياسات storage.objects والتحقق من النوع والحجم والمالك.
6. **الرصد والاستجابة:** سجل تدقيق للأحداث الإدارية والأمنية دون كلمات مرور أو access/refresh tokens، مع خطة نسخ واستعادة واستجابة للحوادث.

## ما تحقق في الفرع حتى الآن
- طبقة domain تحتوي على قاعدة أولية تمنع منطقياً تقديم تفاوض على شحنة غير مفتوحة أو مملوكة للمستخدم نفسه؛ هذه ليست بديلاً عن RLS أو فحص قاعدة البيانات.
- إنشاء حمولة إدراج الشحنة عبر allow-list، مع اشتقاق owner_id من المستخدم الذي أعادته جلسة Supabase.
- توجد اختبارات وحدات لقواعد أهلية التفاوض وحماية حقول إدراج الشحنة.
- أضيفت سياسة CSP مقيّدة داخل HTML مع سياسة Referrer، واختبار متصفح يتحقق من وجودها ومنع `unsafe-eval`.
- أصبحت رسائل أخطاء الواجهة عامة في مسارات تحميل الشحنات والدخول والاستعادة والنشر لتقليل كشف تفاصيل Supabase وقاعدة البيانات.
- CI يحتوي على فحص حدود الاعتماديات، وفحص TypeScript والاختبارات والبناء واختبارات Playwright وAxe؛ يجب مراجعة نتيجة تشغيل فعلية لكل commit قبل اعتمادها.

## ما لم يُعتمد بعد
- لم تكتمل مطابقة مخطط negotiations/trips مع قاعدة البيانات الحية؛ لذلك لم تُكتب عمليات تفاوض أو قبول/رفض أو إنشاء رحلة مرتبطة بالمخطط.
- لا يُفترض أن جميع سياسات RLS أو قيود Storage الحالية تحقق كل الضوابط أعلاه؛ يلزم تدقيق مباشر واختبارات سلبية لكل دور.
- لم يُنجز اختبار اختراق أو فحص أمني مستقل، ولا تم اعتماد شهادة أمنية.
- لم يُعتمد بعد مسار إدارة تفعيل الأدوار أو إدارة مفاتيح التشغيل والإشعارات.

## بوابة القبول الأمني
لا يُعلن عن اكتمال الحماية قبل:
1. توثيق الجداول والأعمدة والقيود والسياسات والـ grants والوظائف والـ triggers وStorage من المصدر الحي.
2. اختبارات وصول مباشر عبر API لكل دور، بما في ذلك الحالات المرفوضة.
3. اختبارات التزامن والتكرار والتلاعب بالمعرفات والحالات.
4. فحص الأسرار والاعتماديات وثغرات XSS والملفات.
5. اختبار النسخ الاحتياطي والاستعادة وخطة التراجع.
6. مراجعة بشرية للنتائج قبل أي نشر.

## قيود السلامة
لا تُنفذ أي SQL أو migration على قاعدة الإنتاج أثناء هذا العمل. لا تُضاف خدمة مدفوعة أو مفتاح سري. كل اختبار هجومي يقتصر على بيئة يملكها المشروع ومصرح بها. هذه الوثيقة خطة وضوابط مستهدفة وليست ادعاءً بأن التطبيق آمن أو أنه اجتاز اختبار اختراق.
## حدود الحماية في الاستضافة الحالية

- سياسة CSP المضافة هي meta policy مناسبة للاستضافة الثابتة؛ لا يمكنها فرض `frame-ancestors` أو كل خصائص HTTP response headers. يلزم ضبط رؤوس HTTP من منصة الاستضافة عند الانتقال إلى استضافة تسمح بذلك.
- سياسة CSP الحالية تسمح باتصالات HTTPS وWebSocket إلى نطاقات Supabase الفرعية فقط، ويجب تحديثها بمراجعة إذا تغير مزود المصادقة أو نطاق API.
- لا تُعد رسائل الخطأ العامة بديلاً عن تسجيل داخلي آمن أو مراقبة الخادم.
