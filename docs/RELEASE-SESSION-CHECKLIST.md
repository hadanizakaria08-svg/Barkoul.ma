# Barkoul.ma — قائمة اختبار جلسة المراجعة والإطلاق

هذه القائمة مرافقة لفرع الاختبار. لا تنفذ أي تغيير في قاعدة الإنتاج أو إعدادات الدفع أو الأسرار. الاختبارات التي تكتب بيانات يجب أن تستخدم حسابات اختبار وسجلات تجريبية معروفة، ثم تنظف سجلات الاختبار فقط بعد التحقق من ملكيتها.

## 1) بوابات آلية يجب أن تكون خضراء قبل الدمج
- [ ] Barkoul CI: typecheck، اختبارات domain، service worker، Shield X lab، build.
- [ ] Validate Barkoul pages: فحص ملفات الصفحات القديمة والروابط/البنية.
- [ ] Playwright: RTL، العنوان، روابط التنقل، واجهة الدخول والتسجيل واستعادة كلمة المرور، حقول الشحنة، البحث، غرفة المدير للزائر.
- [ ] Responsive: 320، 360، 375، 390، 414، 768، 1024، 1280، 1440px دون تمرير أفقي.
- [ ] Accessibility: axe WCAG 2.2 AA على الشاشة الأولى والصفحة العامة.
- [ ] Security/dependency audit: لا ثغرات حرجة/عالية غير معالجة ولا أسرار في الملفات.
- [ ] Native builds: Android debug APK وWindows portable build وiOS simulator build؛ سجّل بوضوح ما هو unsigned وما يحتاج توقيعاً أو حساب متجر.

## 2) اختبار الوظائف العامة (لا يحتاج حساباً)
- [ ] فتح الصفحة بالعربية RTL، ظهور الشعار والخريطة والشاحنات والأزرار.
- [ ] الضغط على «أبحث عن شحنة» ينقل إلى البحث، و«أنشر شحنة» ينقل إلى نموذج النشر.
- [ ] البحث من مدينة وإلى مدينة ونوع شاحنة؛ جرّب نتائج موجودة ونتيجة فارغة.
- [ ] تحديث قائمة الشحنات ورسالة حالة التحميل/الاتصال.
- [ ] الزائر لا يستطيع النشر ولا يرى أدوات الإدارة أو بيانات خاصة.

## 3) اختبار الحسابات — بحسابات اختبار فقط
- [ ] إنشاء حساب مستخدم عادي ببريد اختبار يمكن الوصول إليه.
- [ ] تأكيد سلوك تأكيد البريد كما هو مضبوط في Supabase.
- [ ] تسجيل الدخول والخروج، تحديث الصفحة، واستمرار/انتهاء الجلسة.
- [ ] استعادة كلمة المرور والتحقق من رابط العودة.
- [ ] حساب مستخدم عادي لا ينشر شحنة قبل اعتماد الدور.
- [ ] إرسال طلب دور صاحب بضائع أو سائق؛ تكرار الطلب لا ينشئ طلبات غير مقصودة.
- [ ] تأكيد أن تبديل الحساب يمسح الدور السابق ولا يورث صلاحياته.

## 4) اختبار صاحب البضاعة والسائق والإدارة
باستخدام حسابات منفصلة مع أدوار معتمدة مسبقاً، دون تعديل أدوار الإنتاج:
- [ ] صاحب البضاعة ينشر شحنة صحيحة بتاريخ مستقبلي؛ تظهر مرة واحدة في القائمة.
- [ ] التحقق من رفض الحقول الفارغة والتاريخ الماضي والقيم غير الصحيحة.
- [ ] مستخدم عادي/سائق لا يستطيع نشر شحنة عبر الواجهة أو استدعاء API مباشرة.
- [ ] السائق يرى الشحنات المفتوحة ويمكنه إرسال عرض/تفاوض وفق قواعد التطبيق.
- [ ] لا يستطيع السائق تعديل شحنة لا يملكها أو قبول عرض نيابة عن طرف آخر.
- [ ] صاحب الشحنة يرى التفاوضات الخاصة بشحنته فقط، ولا يرى تفاوضات الآخرين.
- [ ] قبول عرض واحد فقط عند المحاولات المتزامنة؛ لا تنشأ رحلتان لنفس القبول.
- [ ] حالات الرحلة المسموحة فقط: agreed → loading → in_transit → delivered، مع مسارات الإلغاء المسموحة.
- [ ] الإدارة وحدها تستطيع مراجعة طلبات الأدوار والوثائق ورؤية لوحة الإدارة.
- [ ] الحساب غير الإداري لا يستطيع فتح وظائف الإدارة عبر URL أو API أو تغيير role بنفسه.

## 5) التخزين والوثائق
- [ ] bucket وثائق السائقين خاص وليس عاماً.
- [ ] رفع PDF/JPEG/PNG/WEBP ضمن حد الحجم المعلن ينجح لحساب مالك الوثيقة.
- [ ] رفض الملفات غير المسموحة أو الكبيرة.
- [ ] مستخدم آخر وزائر لا يستطيعان قراءة الوثيقة أو تنزيلها أو استبدالها.
- [ ] الإدارة المخولة فقط تستطيع مراجعة حالة الوثيقة.
- [ ] لا تظهر روابط عامة أو بيانات شخصية في قائمة الشحنات.

## 6) العمولات وسلامة العمليات
- [ ] تحقق من احتساب 10 دراهم على صاحب البضاعة و20 درهماً على السائق بعد شحنة ناجحة فقط.
- [ ] تكرار callback/الطلب لا ينشئ رسوماً مكررة؛ اختبر idempotency.
- [ ] لا تعرض الواجهة أن الدفع الإلكتروني متاح ما لم تكن بوابة الدفع مهيأة ومختبرة فعلياً.
- [ ] النقد/التسجيل الإداري لا يُسجل كتحصيل مؤكد إلا بعد إثبات التحصيل.
- [ ] لا تستخدم أموالاً حقيقية أو بيانات دفع حقيقية في الاختبار.

## 7) Shield X — مختبر معزول
- [ ] اختبارات Phantom Room: بيانات اصطناعية فقط ونطاقات .invalid.
- [ ] التصنيف يرصد فقط ولا يحظر أو يحذف.
- [ ] EvidenceChain يكتشف التلاعب ويحجب الحقول الحساسة.
- [ ] Phantom Flash رسالة نصية فقط ولا يطلب الكاميرا.
- [ ] Chain System يعزل الوحدة المعطوبة، يستبدلها بمصدر موثوق، ويفحص سلامتها قبل إعادة الاتصال.
- [ ] فشل الاستبدال يبقي الوحدة معزولة ولا يعطل identity-core.
- [ ] لا اتصال بالمختبر إلى Supabase الإنتاجي أو أسرار GitHub أو ملفات العملاء.
- [ ] لا تدّعِ أن Coraza/WAF أو CrowdSec أو Wazuh أو Sentinel AI منشورة؛ الوثيقة الحالية تصفها كتصميم/متطلبات حتى يتم تركيبها واختبارها على ingress/hosts حقيقية.

## 8) اختبارات تتطلب بيئة اختبار خارج الإنتاج
لا تُجرى على قاعدة الإنتاج. يلزم مشروع Supabase staging منفصل أو بيانات اختبار معتمدة:
- [ ] اختبارات RLS سلبية لكل دور (anon/user/owner/driver/admin).
- [ ] IDOR، role escalation، تزوير owner_id/driver_id، والوصول إلى وثائق الغير.
- [ ] التفاوض المتزامن والقبول المتزامن وتكرار أحداث العمولة.
- [ ] النسخ الاحتياطي والاستعادة إلى مشروع معزول.
- [ ] تدوير الجلسات وإبطالها بعد الخروج أو تغيير الصلاحيات.

## 9) بوابة قرار الإطلاق
- [ ] كل بوابات CI والاختبارات المطلوبة مكتملة على آخر commit للـPR نفسه.
- [ ] مراجعة التقرير والواجهة والنسخة التجريبية من المالك.
- [ ] مراجعة المتطلبات الخارجية: مفاتيح البيئة، إعدادات Supabase، توقيع Android/Windows، Apple signing/App Store.
- [ ] موافقة صريحة على الدمج والنشر بعد المراجعة.
- [ ] بعد النشر: اختبار رابط Pages، تسجيل الدخول، البحث، النشر، الصلاحيات، وعدم وجود أخطاء Console/Network.
- [ ] حفظ commit النشر وروابط artifacts ونتائج الاختبارات كسجل إصدار.

## حدود الإثبات
نجاح CI لا يثبت وحده سلامة RLS على كل دور، ولا يعد اختبار اختراق، ولا يثبت جاهزية متاجر التطبيقات. أي اختبار يتطلب حسابات أو أسراراً أو مشروع staging أو توقيعاً خارجياً يُسجل كمتطلب منفصل ولا يُعلَن نجاحه بالتخمين.
