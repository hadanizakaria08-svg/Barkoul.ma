# Barkoul.ma — مخطط النسخة الشاملة الموحدة

> هذه الوثيقة محفوظة في فرع تطوير مستقل rebuild/unified-platform. لا تغيّر الموقع المنشور أو قاعدة بيانات Supabase، ولا تحتوي على أسرار أو مفاتيح خاصة.

## 1. الهدف

بناء منتج واحد متعدد المنصات يخدم السوق المغربي، مع مشاركة أكبر قدر ممكن من الواجهة ومنطق العمل بين:
- الويب ونسخة PWA القابلة للتثبيت.
- Android وiOS عبر Capacitor.
- Windows عبر Tauri.

**قاعدة القرار:** كود مشترك واحد، مع أغلفة بناء خاصة بكل منصة عند الحاجة. لا نعد بأن نشر المتاجر مجاني؛ رسوم حسابات المطورين ومتطلبات البناء تُراجع قبل أي تسجيل أو دفع.

## 2. التقنية المقترحة

- **Frontend:** React + TypeScript + Vite.
- **التصميم:** RTL عربي أولاً، تصميم أزرق/أبيض، متجاوب مع الهاتف والكمبيوتر، مع قابلية إضافة الفرنسية.
- **PWA:** تثبيت الويب، manifest، service worker وتخزين محدود وآمن للملفات الثابتة فقط.
- **Android/iOS:** Capacitor لتغليف تطبيق الويب المشترك وإضافة قدرات الجهاز عند الحاجة.
- **Windows:** Tauri لتطبيق سطح مكتب خفيف يستعمل الواجهة ومنطق العمل نفسيهما.
- **Backend:** Supabase الحالي (Auth + PostgreSQL + RLS + Storage عند اعتماده).
- **الاستضافة الأولية:** GitHub Pages للواجهة الثابتة، مع احترام حدود GitHub Pages وSupabase Free. لا نعتمد على وظائف خادمية غير متاحة في الاستضافة الثابتة.

هذه بنية مقترحة وليست أمراً بتغيير المشروع الحالي. نثبت الإصدارات والأدوات بعد فحص التوافق وإنشاء نموذج بناء تجريبي.

## 3. وحدات التطبيق

1. **الحسابات والملفات الشخصية:** التسجيل والدخول والخروج واستعادة الحساب، أدوار المستخدم والسائق وصاحب البضاعة، الملف الشخصي.
2. **الشحنات:** الإنشاء، التعديل المسموح، الإغلاق، البحث والتصفية حسب الانطلاق والوصول ونوع الحمولة والشاحنة والتاريخ.
3. **السائقون والمركبات:** أنواع المركبات، بيانات المركبة، وثائق التحقق وحالة مراجعتها.
4. **التفاوض:** تقديم عرض، قبول/رفض/سحب العرض، منع التفاوض على شحنة مغلقة أو مع صاحبها، وحفظ سجل الحالة.
5. **الرحلات:** إنشاء الرحلة بعد الاتفاق، مراحل التحميل والنقل والتسليم والإلغاء، وإثبات إتمام الخدمة.
6. **الاتصال:** إظهار وسائل الاتصال وفق قواعد العمل وبعد تحقق شروط العملية؛ لا كشف بيانات خاصة في قوائم التصفح العامة.
7. **العمولات:** تسجيل استحقاق 10 MAD على صاحب الشحنة و20 MAD على السائق عند تحقق تعريف «الشحنة الناجحة» الذي سنعتمده. لا تُحسب العمولة من واجهة المتصفح وحدها.
8. **التقييمات والبلاغات:** لا تُفتح إلا بعد ربطها برحلة حقيقية، مع مكافحة التقييمات الوهمية وإساءة الاستخدام.
9. **الإشعارات:** إشعارات داخل التطبيق أولاً؛ ثم البريد أو Push أو WhatsApp API فقط بعد دراسة التكلفة والموافقة.
10. **لوحة الإدارة:** مراجعة الحسابات والوثائق والشحنات والبلاغات والرحلات وسجلات التدقيق، بصلاحيات إدارية من الخادم/قاعدة البيانات لا بمجرد إخفاء زر في الواجهة.

## 4. الحماية — متطلبات غير قابلة للتجاوز

- تفعيل RLS والتحقق من كل سياسة على الجداول التي يصل إليها العميل.
- أقل صلاحية ممكنة لكل دور؛ عدم منح المستخدم صلاحية تعديل دوره أو ملكية السجلات.
- عدم وضع service_role أو مفاتيح سرية أو كلمات مرور في ملفات الواجهة أو مستودع GitHub.
- المفتاح العام/Publishable Key وحده لا يمثل حماية؛ الأمان الفعلي في RLS والقيود والتحقق الخادمي.
- التحقق من الملكية والحالة والانتقالات المسموحة داخل PostgreSQL أو Edge Functions موثوقة، وليس عبر شروط JavaScript فقط.
- العمليات المالية والعمولات يجب أن تكون ذرية وقابلة للتدقيق، مع منع التكرار (idempotency) وعدم الثقة في السعر المرسل من المتصفح.
- حماية من XSS وحقن المدخلات، والتحقق من البيانات على الخادم، وتحديد معدلات الطلبات للعمليات الحساسة.
- سجلات تدقيق للأحداث الإدارية والأمنية دون تسجيل كلمات المرور أو الرموز السرية.
- رفع الملفات لا يُفعّل قبل اعتماد Buckets وسياسات Storage وفحص نوع الملف وحجمه وملكيته.
- نسخ احتياطي وخطة استعادة مجرّبة؛ لا نعد أن النسخ الاحتياطي التلقائي متاح مجاناً قبل التحقق من خطة Supabase الفعلية.

## 5. قواعد العمل التي تحتاج تثبيتاً قبل البرمجة

- متى تعتبر الشحنة «ناجحة» وتستحق العمولة؟
- هل تُحصّل العمولتان نقداً خارج المنصة أم إلكترونياً أم بالطريقتين؟
- كيف نثبت دفع العمولة النقدية ونمنع تسجيل الدفع مرتين؟
- متى يُكشف رقم الهاتف أو وسيلة التواصل؟
- ما شروط إلغاء الشحنة أو الرحلة والنزاع؟
- ما الوثائق المطلوبة للسائق والمركبة، ومن يراجعها؟
- هل يسمح لصاحب الشحنة بنشر شحنة دون سعر، كما في النموذج الحالي؟

القيم التجارية المبدئية المحفوظة: 10 دراهم على صاحب الشحنة و20 درهماً على السائق لكل نقل ناجح. لا نربط بوابة دفع قبل اختيار مزود مناسب والتحقق من شروطه ورسومه القانونية والتجارية.

## 6. التعامل مع قاعدة البيانات الحالية

قاعدة البيانات الحالية هي مصدر الحقيقة، ولا ننشئ مخططاً بديلاً من تخمينات. قبل أي Migration:
1. إكمال تدقيق الوظائف والصلاحيات وStorage.
2. جرد الأعمدة والقيود والمفاتيح والفهارس والسياسات الفعلية.
3. حسم اختلاف نوع cargos.id عن مفاتيح cargo_id في الجداول المرتبطة بعد التحقق من كل العلاقات والبيانات.
4. مطابقة كود الواجهة مع أسماء الأعمدة والسياسات الموجودة.
5. كتابة migrations صغيرة، قابلة للمراجعة والتراجع، واختبارها على مشروع/بيئة منفصلة أولاً.

الجداول التي ظهرت في المراجعات السابقة تشمل: profiles, cargos, negotiations, trips, driver_documents, admin_users, admin_audit_log. وجود الجدول لا يعني أن تصميمه النهائي أو صلاحياته قد اعتُمدت.

## 7. هيكل ملفات مقترح

    apps/
      web/                 # React + TypeScript + Vite + PWA
      mobile/              # Capacitor configuration and native projects
      desktop/             # Tauri configuration for Windows
    packages/
      domain/              # Types, validation, state transitions, business rules
      data/                # Supabase client and repositories
      ui/                  # Shared RTL components and design tokens
      config/              # Shared lint, TypeScript and build configuration
    supabase/
      migrations/          # Reviewed, incremental SQL migrations
      functions/           # Trusted server-side operations
    tests/
      unit/
      integration/
      security/
    docs/
      ARCHITECTURE.md
      DATA-MAP.md
      SECURITY-THREATS.md
      RELEASE-CHECKLIST.md

لا ننقل المشروع إلى هذا الهيكل قبل أن نجهز نسخة احتياطية ونثبت نموذج البناء والاتصال بقاعدة البيانات الحالية.

## 9. معايير قبول النسخة

- لا يستطيع مستخدم قراءة أو تعديل بيانات خاصة لا تخصه.
- لا يستطيع مستخدم رفع صلاحياته أو تزوير دور إداري.
- لا يمكن التفاوض مع صاحب الشحنة على شحنته أو على شحنة مغلقة.
- لا يمكن إنشاء رحلتين أو تحصيل عمولة مكررة لنفس الحدث.
- كل انتقال حالة موثق ومسموح به.
- الواجهة تعمل على شاشات الهاتف والكمبيوتر مع RTL سليم.
- تعطل الشبكة لا يؤدي إلى عرض نجاح كاذب أو تكرار إرسال العملية.
- يمكن الرجوع إلى إصدار سابق دون فقدان غير مقصود للبيانات.
- لا يتم نشر أي إصدار أو إجراء Migration على الإنتاج دون موافقة المستخدم.

## 10. ملاحظات من فحص الكود الحالي

- المستودع الحالي يحتوي على index.html وadmin.html وindex-v2.html وREADME.md.
- index.html الحالي صفحة HTML واحدة تعتمد على Supabase JS من CDN، وفيها الدخول والتسجيل وتصفح الشحنات ونشرها.
- الواجهة الحالية تستخدم ألواناً خضراء/برتقالية، بينما الاتجاه النهائي المطلوب أزرق/أبيض.
- الصفحة تقرأ حقولاً مثل origin_city وdestination_city وgoods_type وoffered_price_mad؛ يجب مطابقتها مع المخطط الحي قبل إعادة استخدام أي استعلام.
- يجب اختبار سلوك الجلسة بعد الدخول والخروج، وعدم الاعتماد على حالة واجهة المستخدم كحد أمني.
- لا ننسخ أي SQL قديم إلى الإنتاج؛ نتائج التدقيق الأحدث هي المرجع، وأي تغيير يحتاج مراجعة مستقلة.
